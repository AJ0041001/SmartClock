# 串口通讯例程

验证**鲁班猫 ↔ STM32** 之间的串口通讯。

这两个文件**不依赖项目里的任何其它模块**，所有逻辑都写在文件内部 ——
出问题时容易定位，你也通读一遍就能完整理解协议。

---

## 文件

| 文件 | 作用 |
|---|---|
| `serial_ping.py` | 通信测试客户端（真正跟 STM32 说话的那个） |
| `virtual_stm32.py` | 虚拟 STM32（用伪终端模拟，**没有硬件也能测**） |

---

## 第一步：没有硬件时，先验证软件

这一步能排除所有软件层面的问题。**强烈建议先做这一步**，
否则真到了硬件上出问题，你会分不清是代码还是接线。

### 终端 1：启动虚拟 STM32

```bash
# 在项目根目录（包含 src/ scripts/ 的那一层）执行
cd Visual/color_block
python3 examples/virtual_stm32.py
```

它会打印一个虚拟串口路径，例如：

```
  虚拟串口已创建：/dev/pts/5

  在**另一个终端**里运行：
      python3 examples/serial_ping.py --port /dev/pts/5
```

### 终端 2：对虚拟串口跑测试

```bash
# 单帧通讯
python3 examples/serial_ping.py --port /dev/pts/5

# 坏帧检测（验证对方 CRC 校验在工作）
python3 examples/serial_ping.py --port /dev/pts/5 --bad-crc

# 扫描（挡住板会"移动"）
python3 examples/serial_ping.py --port /dev/pts/5 --sweep
```

**期望结果：**

```
  发送: AA 55 06 01 D4 00 42 02 00 7D   (中心坐标 212,578)
  回传: b'OK\r\n'
  结果: 收到 OK —— 通讯正常

✅ 通讯正常
```

**如果虚拟环境都不通，那就是代码问题，别去动硬件。**

---

## 第二步：接上真实硬件

### 接线（三根线）

| USB-TTL | STM32 | 说明 |
|---|---|---|
| TX | RX | **必须交叉** |
| RX | TX | **必须交叉** |
| GND | GND | **必须共地** |
| VCC | 不接 | 两边各自供电 |

> ⚠️ 最常见的三个错误：TX 接 TX、忘记共地、两边都供 3.3V 造成倒灌。

### 关于板载 UART

实测你板子上**所有 10 个板载 UART 在设备树里都是 `disabled`**，
`/dev/ttyS*` 一个都不存在。所以：

- **推荐**：用 USB-TTL 转换器 → 插上就有 `/dev/ttyUSB0`，零配置
- 或者：按 `docs/部署与接线.md` 启用 40pin UART 设备树插件

## 第三步：测试

### 1. 看看有哪些串口

```bash
python3 examples/serial_ping.py --list
```

### 2. 自动找出哪个串口接了 STM32

```bash
python3 examples/serial_ping.py --probe
```

**判据：谁能正确回 `OK`，谁就是接到 STM32 的那个。**

```
  测试 /dev/ttyUSB0 ... ✅ 收到 OK
  测试 /dev/ttyS0 ... 无响应

✅ 找到目标：/dev/ttyUSB0
```

### 3. 单帧通讯

```bash
python3 examples/serial_ping.py --port /dev/ttyUSB0
```

### 4. 让挡板动起来（最有说服力的验证）

```bash
python3 examples/serial_ping.py --port /dev/ttyUSB0 --sweep
```

**盯着 STM32 的屏幕**，红色挡板应该从左扫到右。

```
  [ 1/9] X=35   AA 55 06 01 23 00 24 01 00 xx  → OK
  [ 2/9] X=79   ...                              → OK
  ...
```

如果每帧都回 OK，**且挡板真的跟着动了**，链路就完全通了。

### 5. 回环测试（定位故障在哪一端）

把 USB-TTL 的 **TX 和 RX 用杜邦线短接**，然后：

```bash
python3 examples/serial_ping.py --port /dev/ttyUSB0 --loopback
```

| 结果 | 含义 |
|---|---|
| ✅ 完整回环 | 本地串口正常 → 问题在对端或接线 |
| ❌ 收不到 | 本地串口本身有问题 |

## 故障排查

### 打不开串口（Permission denied）

```bash
sudo usermod -aG dialout $USER
# 然后必须注销重新登录
```

### 一直收不到 OK

按这个顺序查（从最常见的开始）：

| # | 检查项 | 怎么查 |
|---|---|---|
| 1 | **TX/RX 接反了吗** | 交换两根线再试（最常见） |
| 2 | **共地了吗** | 万用表量两边 GND 是否导通 |
| 3 | 波特率一致吗 | 两边都应是 115200 |
| 4 | STM32 在运行吗 | 屏幕有显示吗？按键控制能用吗？ |
| 5 | 固件启用了接收吗 | 代码里有没有调 `BSP_GameSerial_Start()` |
| 6 | 选对设备了吗 | `--probe` 自动找 |

### 收到 ERROR 而不是 OK

说明能通信，但帧被判为无效：

- **波特率不一致** → 收到乱码，CRC 必然失败（最常见）
- 固件版本与本仓库不一致 → 核对 `Code/BSP/Src/bsp_board.c` 的 CRC 实现

用**已知正确的帧**验证：

```bash
python3 examples/serial_ping.py --port /dev/ttyUSB0 --bad-crc
```

这帧的 CRC 是由固件原版 C 函数算出来的。如果它也被判 ERROR，
问题一定在波特率或接线，而不是你的坐标数据。

## 协议速查

发送的帧固定 10 字节：

```
AA 55 06 TYPE X_L X_H Y_L Y_H 00 CRC8
│  │  │  │    └──┬──┘ └──┬──┘ │   └── 校验（覆盖字节 2~8，共 7 字节）
│  │  │  │       │       │    └────── 保留
│  │  │  │       │       └─────────── Y 坐标（小端）
│  │  │  │       └─────────────────── X 坐标（小端）
│  │  │  └─────────────────────────── 类型：01=串口+按键，02=仅按键
│  │  └────────────────────────────── 长度，固定 6
│  └───────────────────────────────── 帧头 2
└──────────────────────────────────── 帧头 1
```

- **CRC-8**：初值 `0x00`，多项式 `0x07`
- **STM32 回传**：合法 → `OK\r\n`，非法 → `ERROR\r\n`

**坐标范围**（挡板中心）：

```
X: 35 .. 389
Y: 6  .. 578
```

超出范围是安全的 —— STM32 会自动限幅，把挡板贴到最近的边界。

## 实测参考帧

由固件原版 C 函数计算得出，可直接用串口助手发送：

```
AA 55 06 01 D4 00 42 02 00 7D     中心坐标 (212, 578)，TYPE=01
```

STM32 应回 `OK`。回 `ERROR` 说明波特率或接线有问题。
