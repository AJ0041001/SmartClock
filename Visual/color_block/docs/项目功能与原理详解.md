## 一、项目背景与要解决的问题

### 1.1 任务是什么

做一个"用实物控制游戏"的系统：屏幕上有一个接星星的小游戏，
玩家手里拿一张**红色卡片**在摄像头前移动，游戏里的红色挡板
就要跟着卡片同步移动。

```
   实物世界                              数字世界
  ┌───────────┐                        ┌──────────────┐
  │  红卡      │   USB 摄像头            │  STM32 屏幕   │
  │  （手拿）  │ ──────────▶  鲁班猫4 ──▶│  480×800 LCD  │
  └───────────┘   图像        （识别+算坐标）  串口   │  红色挡板跟随 │
                                              └──────────────┘
```

### 1.2 为什么不用现成的方案

| 备选做法 | 为什么没选 |
|---|---|
| 纯 HSV 颜色阈值 | 反光、阴影、白平衡漂移都会让阈值失效；黑底红卡场景下不如学习类方法稳 |
| 在 PC 上跑 YOLO 再传坐标 | 板子本身就是边缘设备，要的就是**端侧实时**，不依赖网络 |
| 用 `rknn_toolkit_lite2` 官方库 | 官方轮子只提供到 **cp312**，板子是 **Python 3.14**，装不上（下文 7.1 详述） |
| 用 tkinter 做参数界面 | 板子没装 `python3-tk`，而且 tkinter 与 OpenCV 各有事件循环，混用会卡死 |

### 1.3 三个技术难点（也是本项目的价值点）

1. **端侧实时推理**：7 MB 的检测模型要在 NPU 上跑到 16 fps 以上，
   且要绕开官方 Python 库的版本限制。
2. **坐标精度**：卡片在画面边缘时，检测到的"中心"会偏离真实中心，
   直接导致游戏里的挡板"到不了最边上"——这是本项目最核心的改进点。
3. **软硬件闭环**：视觉端算出的坐标要通过一套自定义二进制协议
   可靠地送到 STM32，位错一位就全盘失效。

## 二、系统总体架构

### 2.1 数据流（一帧的完整生命周期）

```
 ①采集          ②检测            ③裁ROI         ④映射           ⑤组帧        ⑥下发
┌───────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌────────┐   ┌───────┐
│USB摄像头│──▶│YOLO/RKNN │──▶│ 按 B 裁剪 │──▶│ 双ROI映射 │──▶│10字节帧 │──▶│STM32  │
│640×480 │   │  NPU 推理 │   │ letterbox│   │+EMA+死区  │   │ +CRC-8 │   │驱动挡板│
└───────┘   └──────────┘   └──────────┘   └──────────┘   └────────┘   └───────┘
   16.7fps       ~20ms/帧        640×640      归一化+限幅    10 byte      回 OK
```

### 2.2 软件分层

| 层 | 模块 | 职责 |
|---|---|---|
| 采集层 | `camera.py` | UVC 摄像头封装（V4L2/OpenCV），暴露实际分辨率与帧率 |
| 推理层 | `rknn_ctypes.py`、`yolo.py`、`card_detector.py` | NPU 上下文管理、letterbox、输出解码、NMS |
| 降级层 | `detector.py` | HSV 阈值分割（模型不可用时的备选引擎） |
| 算法层 | `mapper.py` | 双 ROI 坐标映射、EMA 平滑、死区 |
| 交互层 | `roi_editor.py`、`ui_buttons.py`、`text_cjk.py` | 画面内控制面板、自绘按钮、中文渲染 |
| 通信层 | `protocol.py`、`serialport.py` | 10 字节帧 + CRC-8，纯 `termios` 串口 |
| 编排层 | `pipeline.py`、`config.py` | 依赖注入的主流水线、YAML 配置与校验 |

**架构上刻意做的三个选择**：

- **依赖注入**：流水线不自己 new 摄像头和串口，而是接收两个对象。
  于是可以注入"假摄像头 + 假串口"，在**没有硬件的机器上跑完整端到端测试**。
- **双引擎可切换**：`detector.engine: yolo | hsv`，两种检测器接口完全一致，
  切换引擎不需要改流水线代码；HSV 引擎是模型失效时的现场降级方案。
- **纯函数化算法层**：ROI 状态机、按钮布局、命中判定都不依赖 OpenCV，
  可以完整单元测试；只有真正绘制时才调用 `cv2`。

## 三、硬件与运行环境

| 项目 | 具体内容 | 备注 |
|---|---|---|
| 主控 | 鲁班猫 4 V1R0（RK3588S，8 核，aarch64） | 片上 NPU 已启用（`CONFIG_ROCKCHIP_RKNPU=y`） |
| NPU 节点 | `/dev/dri/renderD129`，运行时库 `librknnrt.so` | 板子自带，也可随包携带做兜底 |
| 摄像头 | USB UVC，640×480 MJPG | 实测协商到 120 fps（高于配置值，亮度正常故不处理） |
| 串口 | **USB-TTL 转串口**，`/dev/ttyUSB0` @115200 | 见下方说明 |
| 下位机 | STM32，固件 `Code/`，CRC 实现 `BSP/Src/bsp_board.c:208` | 收到帧回 `OK\r\n` |

**为什么必须用 USB-TTL 而不是板载串口**：查设备树发现板子上
**10 个片上 UART 一个都没使能**，所以只能用 USB 转串口模块
（ch341 / cp210x / ftdi_sio / pl2303 驱动都已内置）。

**权限**：串口需要把用户加入 `dialout` 组（`sudo usermod -aG dialout $USER`），
**注销重新登录**才生效。

## 五、关键原理详解（PPT 重点页素材）

### 5.1 letterbox：为什么不能直接 resize

模型输入固定 640×640，而摄像头是 640×480（4:3）。如果直接拉伸到正方形，
物体会在纵向被压扁 **25%**，检测精度下降。

正确做法是按长边等比缩放，再把短边用灰边补齐：

```
  640×480  ──等比缩放 0.75──▶  480×360  ──居中填灰边──▶  640×640
                                                          ↑ 上下各 140 像素灰边
```

反变换时要把填充量减掉：

```
原图坐标 = (模型坐标 − pad) / scale
```

### 5.2 检测框解码：cxcywh ≠ xyxy

YOLO 系列导出的原始输出是**中心点 + 宽高**，不是对角线坐标：

```
输出张量：[1, 5, 8400]
           │  └── 8400 个候选框（3 个尺度 × 多个网格）
           └───── 每框 5 个数：cx, cy, w, h, conf
```

解码公式（把归一化值还原到 640×640 输入图坐标）：

```
x1 = cx − w/2      y1 = cy − h/2
x2 = cx + w/2      y2 = cy + h/2
```

> ⚠️ **踩过的坑**：仓库早期 README 把输出写成 `xyxy`，按 `xyxy` 解析会导致
> 检测框严重错位**且不报错**。本项目实现了格式自动判别（`box_format: auto`），
> 并用真实模型输出验证：中心点与宽高都落在合理区间，而"左上角"会出现
> 负值——据此判定为 `cxcywh`。

### 5.3 NMS 非极大值抑制

同一个卡片会被多个尺度/网格同时检出，需要去重：

1. 按置信度从高到低排序
2. 取出最高分的框，计算它与其余框的 **IoU**（交并比）
3. 删掉 IoU 超过阈值（0.45）的框——它们大概率指同一个目标
4. 重复直到没有剩余框

```
IoU = 交集面积 / 并集面积
```

### 5.4 双 ROI：本项目最核心的改进

**问题现象**：游戏里挡板能跟着卡片走、方向也对，但卡片移到画面左右最边上时，
挡板**总差那么一点点贴不到墙**，紧贴边界落下的星星接不到。

**根本原因**：检测区域和映射区域是同一个框时，卡片中心移到框边界，
卡片有一半落在框外，模型只看到剩下的那一半，算出来的中心是
**可见部分的中心**，不是卡片真实中心。

```
   映射区 A（也是旧方案的检测区）
   ┌──────────────────────┐
   │        ┌─────────────┼──────┐
   │        │  只看到这一半 │ 被裁掉 │   ← 真实卡片
   │        └─────────────┼──────┘
   └──────────────────────┘
            ↑
     算出的中心偏到这里 → 挡板离墙差半个卡片宽
```

**解决方案**：拆成两个矩形。

```
   ┌──────────── B：检测区域（绿色虚线）────────────┐
   │   ┌──────── A：映射区域（黄色实线）────────┐   │
   │   │                                       │   │
   │   │            🟥 红卡（完整可见）          │   │
   │   │                                       │   │
   │   └───────────────────────────────────────┘   │
   └───────────────────────────────────────────────┘

   检测用 B → 卡片在 A 边缘时仍完整落在 B 内 → 中心准确
   映射用 A → 中心超出 A 被限幅到边缘 → 正是"挡板贴边"的语义
```

**约束条件（必须满足）**：B 比 A 每边外扩的像素数 `roi_margin`
必须 **大于卡片宽度的一半**。红卡在 640×480 画面里约 90 px 宽，
所以 `roi_margin ≥ 45`，默认取 60。

**效果量化**（`scripts/demo_edge_center.py` 实测）：

| 卡片位置 | 旧方案（B=A）中心误差 | 新方案（B=A+边距）中心误差 |
|---|---|---|
| A 左边界 | 22.5 px | **0.0 px** |
| A 右边界 | 23.0 px | **0.0 px** |
| 明确出界 | 34.0 px | 4.0 px |
| **换算到游戏坐标** | **最坏离墙差 37 像素** | **最坏离墙差 4 像素** |

> "离墙差 37 个游戏像素"就是"接不到边缘星星"的直接原因。

### 5.5 坐标映射数学

游戏侧坐标系（依据固件与文档）：

```
屏幕逻辑尺寸      480 × 800
白色外框          430 × 590，左上角 y = 78，边框 3 px
内部有效区域      424 × 584
挡板尺寸          70 × 13
挡板中心有效范围  X: 35 .. 389      Y: 6 .. 578
```

映射策略是**线性拉伸**：

```
nx = clamp((cam_x − A.x) / A.w, 0, 1)
ny = clamp((cam_y − A.y) / A.h, 0, 1)
game_x = 35 + nx × (389 − 35)
game_y =  6 + ny × (578 −  6)
```

语义非常直观：**卡片位于 A 的左边缘 → 挡板贴左墙**。
所以 A 就是"挡板的物理可动范围"，现场标定很好操作。

### 5.6 EMA 平滑与死区

摄像头检测必然有 ±1~2 像素的抖动，直接转发会让挡板"哆嗦"。

**EMA 指数移动平均**：

```
out = α × new + (1 − α) × prev        α = 0.35
```

α 越大越跟手但越抖；越小越平滑但越滞后。追踪场景 0.3~0.5 合适。

**死区**：位移小于阈值（2 游戏像素）视为静止，直接输出上一次的值。
抖动通常只有 1~2 像素，死区能把它彻底抹平，让挡板**完全静止**——
比单纯依赖 EMA 更有效。

### 5.7 串口协议与 CRC-8

**帧结构（10 字节定长）**：

| 字节 | 值 | 含义 |
|---|---|---|
| 0 | `0xAA` | 帧头 1 |
| 1 | `0x55` | 帧头 2 |
| 2 | `0x06` | 数据长度 |
| 3 | `TYPE` | `0x01`=串口+按键，`0x02`=仅按键（交还控制） |
| 4 | `X_L` | 挡板中心 X 低字节 |
| 5 | `X_H` | X 高字节 |
| 6 | `Y_L` | Y 低字节 |
| 7 | `Y_H` | Y 高字节 |
| 8 | `0x00` | 保留 |
| 9 | `CRC8` | 校验 |

**CRC-8 参数**：多项式 `0x07`，初值 `0x00`，**只对第 2~8 字节（7 字节）计算**。

**实测示例帧**（挡板中心 212, 578）：

```
AA 55 06 01 D4 00 42 02 00 7D
                        └─ CRC = 0x7D
```

> 串口对接最怕"看着一样但差一位"。本项目把 STM32 固件里的 CRC 函数
> **原样摘录出来编译**，与 Python 实现跑 **10 万组随机向量逐比特比对**，
> 全部一致。这是协议正确性的硬证据。

### 5.8 为什么用 ctypes 直调 NPU

官方 `rknn_toolkit_lite2` 只提供 cp37~cp312 的轮子，板子是 **Python 3.14**，
装不上。于是本项目：

1. 按官方 `rknn_api.h` 用 ctypes 定义结构体（字段顺序、对齐严格对应）
2. 直接 `dlopen("librknnrt.so")`，调用 `rknn_init` / `rknn_inputs_set` /
   `rknn_run` / `rknn_outputs_get`
3. 结构体大小实测校验：`rknn_input`=32、`rknn_output`=24、`rknn_tensor_attr`=376

**关键坑**：`inputs_pass_through` 必须为 0。设成 1 会把 uint8 数据直接喂给
float16 输入节点，输出**全是 NaN** 且不报错。

## 七、工程难点与解决过程（答辩加分项）

### 7.1 NPU 官方 Python 库装不上 → 手写 ctypes 绑定

**问题**：`pip install rknn_toolkit_lite2` 找不到匹配版本。
**排查**：官方只发 cp37~cp312 轮子，板子是 Python 3.14.4。
**解决**：按 `rknn_api.h` 手写 ctypes 结构体与调用，零依赖调 NPU。
**验证**：结构体大小、字段偏移逐项断言；真机推理结果与 ONNX 一致。

### 7.2 模型输出全是 NaN

**现象**：推理返回的框全是 `NaN`，但程序不报错。
**原因**：`inputs_pass_through` 传了 1，uint8 数据被当作 float16 解释。
**解决**：改为 0，让运行时按 `rknn_input` 里声明的类型做转换。

### 7.3 "检测全错"其实是测试脚本用错了坐标格式

**现象**：数据集评估显示 32/32 张 IoU = 0.000，看起来模型完全失效。
**真实原因**：统一的 `Detection.bbox` 是 **(x, y, w, h)**，而评估脚本把它
当成 `xyxy` 喂给了 `iou()`——框变成非法矩形，IoU 自然全 0；
可视化时 `cv2.rectangle` 也画出了巨大的错框。
**解决**：统一用 `Detection.bbox_xyxy` 属性做转换。

> **这段经历在答辩里值得讲**：我一开始先后误判为"输出格式错了"和
> "模型/数据集有问题"，最后才定位到是自己的调用方用错字段。
> 教训是**先验证数据流边界上的契约**，再怀疑算法。

### 7.4 预览窗口弹出来却是全白

**现象**：窗口建好了、画面数据也正常，但窗口里什么都没有。
**原因**：窗口标题含中文（`SmartClock 视觉追踪`）。OpenCV 的 HighGUI
在 Linux（Qt 后端）对非 ASCII 窗口标题支持很差。
**解决**：标题改纯 ASCII，并加了一条 AST 测试防止有人再写回中文。

### 7.5 界面上画不出中文

**原因**：`cv2.putText` 用的是 Hershey 矢量字体，**只支持 ASCII**，
画中文的结果是一串空白（不报错）。
**解决**：用 Pillow 渲染文字成带 alpha 的位图，再混合进 BGR 画面；
带 LRU 缓存，逐帧开销可忽略。缺中文字体时自动降级为英文标签。

### 7.6 界面整块消失（用户实际遇到并反馈）

**现象**：窗口正常、检测正常、坐标在跳，但**两个大框、按钮、操作指引全都没有**。
**原因**：控制面板是在 `pipeline.open()` 里创建的，而 `scripts/main.py`
是自己开摄像头、直接调 `run()`，**从来没调用过 `open()`**。
**解决**：
1. `main.py` 老老实实调用 `pipeline.open()`
2. `run()` 里再调一次**幂等**的 `_ensure_preview_controls()` ——
   不管调用方走不走 `open()`，只要进主循环，面板就一定在
3. 加了完全模仿 `main.py` 用法的回归测试

### 7.7 测试可能覆盖用户的现场标定

**风险**：部分测试建 `RoiEditor` 时没指定配置文件路径，默认会写到
仓库的 `config.yaml`。只要测试里碰到一次"保存"，用户辛苦框好的两个 ROI
就被测试假数据覆盖了。
**解决**：
1. 保存目标可用环境变量 `SMARTCLOCK_CONFIG` 重定向，测试包默认指向 `/dev/null`
2. 代码卫生测试用 AST 扫描：**测试里建 `RoiEditor` 不传 `config_path` 直接失败**
3. 每次跑测试前后比对 `config.yaml` 的 sha256

### 7.8 现场鼠标/键盘的可用性打磨

- 框选过程中**按钮不抢点击**，否则想点画面边缘的角会被按钮吃掉
- 按钮画在**画面内部**，窗口尺寸 = 画面尺寸，小屏幕不会把按钮挤到屏幕外
- 框选时画"橡皮筋"预览矩形 + 实时尺寸，落点看得见
- 检测框贴到 B 边界时 **B 变红报警**，把"参数没调好"变成肉眼可见的信号

## 九、项目创新点总结（答辩结尾可用）

1. **双 ROI 边缘中心校正**：把"检测区域"和"映射区域"解耦，
   用几何约束（B ⊇ A，且外扩量 > 卡片半宽）从根本上消除了
   边缘处中心偏移，实测把最坏中心误差从 34 px 降到 4 px
   （游戏坐标上从"离墙 37 像素"降到 4 像素）。
2. **端侧 NPU 部署不依赖官方 Python 库**：手写 ctypes 绑定，
   绕开轮子版本限制，并用结构体偏移断言保证 ABI 正确。
3. **可现场操作的参数界面**：零依赖的自绘控件 + 中文渲染 +
   键盘两击框选 + 贴边自动告警，把"调参"变成不需要说明书的事。
4. **可验证的工程方法**：CRC 逐比特交叉验证、离线端到端、
   真实指标评估、以及"每个踩过的坑都变成一条回归测试"。

## 十一、预判答辩问题与回答要点

| 问题 | 回答要点 |
|---|---|
| 为什么不用 HSV？ | 反光/阴影/白平衡会让阈值失效；对比实验里 HSV 在卡片倾斜和逆光时容易丢框。HSV 保留为降级引擎。 |
| 为什么不做量化？ | INT8 量化会带来精度损失，而 FP16 在本任务上已能满足 16.7 fps 的实时要求，精度优先。 |
| 16.7 fps 够用吗？ | 游戏挡板是低速目标；STM32 侧有"超时回退按键"机制，20 fps 的发送上限已足够跟手。 |
| 双 ROI 为什么能解决边缘问题？ | 关键在"模型看到的是完整卡片"。只要 B 覆盖卡片在 A 边缘时的整个范围，中心就等于真实中心；映射仍按 A 限幅，所以挡板还能贴边。 |
| `roi_margin` 怎么定？ | 必须 > 卡片半宽。卡片约 90 px 宽 → 至少 45，默认 60 留余量。界面会用"B 变红"提示是否够大。 |
| 中心误差怎么测的？ | 合成图像：已知卡片真实中心 → 按 B 裁剪 → 检测 → 换算回全图 → 与真值比较。见 `demo_edge_center.py`。 |
| 怎么保证和 STM32 的协议一致？ | 把固件 CRC 函数原样编译，与 Python 实现跑 10 万组随机向量逐比特比对。 |
| 为什么不用 pyserial？ | 板子上没装，为了"拷过去就能跑"用标准库 `termios` 自己实现。 |
| 失败模式有哪些？ | 摄像头掉线（重试 60 次后退出）、串口掉线（计数告警不中断）、模型不可用（切 HSV）、无图形界面（关预览）、缺中文字体（降级英文）。 |
| 如果卡片被手挡住一半？ | 检测框中心仍按可见部分计算，会偏移；但双 ROI 保证"出界"不会被误裁，两者是不同问题。可提"部分遮挡下的鲁棒性"作为展望。 |
