# 标定指南

标定是这套方案里**唯一必须现场做、且做完才能用**的环节。房间灯光、
摄像头白平衡、卡片材质、安装角度都会影响结果，预设参数只能保证
"程序跑得起来"，不能保证"检得准"。

## 用哪种引擎，决定标定几步

本项目默认用 **YOLO26 + NPU** 检测红卡（`detector.engine: yolo`）。
模型已经用真实照片训练好、并在测试集上验证过（精确率 100%、召回率
96.97%、中心误差平均 1.0px），所以：

| 引擎 | 需要标定什么 |
|---|---|
| `yolo`（默认） | **只需要第二步**：框 A / B 两个 ROI + 第三步方向手感 |
| `hsv`（降级方案） | 第一步颜色标定 + 第二步 + 第三步 |

**没有特殊理由就跳过第一步。** 只有当你想用 HSV 临时替代模型、
或者怀疑"是不是模型的问题"时，才需要做颜色标定。

---

## 前置：摄像头就位

- 摄像头**固定牢**。追踪期间任何移动都会让 ROI 失效。
- 视野要完整覆盖卡片的活动范围，四周留点余量。
- **避免正对强光源**（窗户、灯管）。逆光会让卡片在画面里发暗、丢细节。
- 自动曝光是抖动的常见来源。能关就关；关不掉的话把
  `mapping.smoothing` 调小一点来抑制。

> 判断现场光照和训练条件差多少，可以看 `--dry-run` 结束时的报告：
> 里面会打印画面亮度均值。训练集是 137.4，现场实测 137.3 —— 差得远
> 就说明该补光或换个角度。

## 第一步：颜色标定（仅 HSV 引擎需要）

### 为什么不能直接用预设色

预设色是按"标准红/绿/蓝"给的区间。现实中：

- 打印出来的红色，H 值可能落在 175 而不是 0
- 灯光偏暖时，同一个卡片的 H 会整体偏移
- 反光会让部分像素的 S/V 飙高

所以**必须现场取色**。

### 方法 1：自动取色（推荐先用这个）

```bash
# 1) 把色块放在视野正中，抓一帧
python3 scripts/color_pick.py --capture assets/captures/s1.jpg

# 2) 让程序自己找画面里最显眼的彩色区域
python3 scripts/color_pick.py --image assets/captures/s1.jpg --auto
```

程序会：

1. 找到画面中面积最大的高饱和区域
2. 统计该区域的 HSV 分布
3. 用**百分位数**（5%~95%）而不是 min/max 推导区间 —— 避免个别
   反光或阴影像素把区间撑得过大
4. **回检**：用推导出的区间重新检测，报告质心、面积、外接框

**看回检结果判断好坏**：

| 回检输出 | 含义 | 下一步 |
|---|---|---|
| `✓ 检出成功，质心 (x, y)` | 区间可用 | 确认位置合理后加 `--write` |
| `与采样点偏差 dx/dy < 10` | 质心很准 | 好 |
| `与采样点偏差` 超过 30 | 可能连到了别的物体 | 检查画面里有没有同色干扰物 |
| `⚠️ 检不出色块` | 区间太窄或有误 | 加大 `--radius` 重试 |
| `❌ 画面里没有找到足够的彩色区域` | 色块不在视野或饱和度过低 | 调 `--saturation_floor` 或手动指定坐标 |

### 方法 2：手动指定采样点

自动模式在画面里有多个彩色物体时会找错。这时手动指定：

```bash
# 用图片查看器打开 s1.jpg 找到色块中心的像素坐标，比如 (320, 240)
python3 scripts/color_pick.py --image assets/captures/s1.jpg --x 320 --y 240
```

### 确认满意后写回配置

```bash
python3 scripts/color_pick.py --image assets/captures/s1.jpg --auto --write
```

会把 `config.yaml` 改成：

```yaml
detector:
  preset: custom
  custom_ranges:
    - lower: [0, 120, 90]
      upper: [10, 255, 255]
    - lower: [170, 120, 90]
      upper: [180, 255, 255]
```

> **红色的特殊性**：红色跨越 H=0/180 边界。程序会自动识别并拆成两段。
> 如果你手动写区间，写成 `lower: [170,...] upper: [10,...]` 是**错的**
> （下界大于上界），必须拆成两段。

### 调最小面积

取色完成后，如果还有误检：

```yaml
detector:
  min_area: 400.0     # 调大，例如 800
```

经验值：一个 40×40 像素的色块约 1600 像素²。色块在画面里多大，
可以用 `preview.py` 里的外接框估算。

## 第二步：双 ROI 标定（A 映射 / B 检测）

画面上要框**两个**矩形，职责不同：

- **A（映射区域，黄色实线）** —— 色块的物理活动范围。它会被线性拉伸到
  挡板中心的有效范围（X: 35..389，Y: 6..578）。
- **B（检测区域，绿色虚线）** —— 送进模型的范围。**必须比 A 大一圈。**

### 为什么必须分成两个

如果两者是同一个框，红卡中心移到 A 的边界时，卡片有一半在框外，模型只看
得到剩下那一半，算出来的中心是**可见部分的中心**而不是真实中心。表现就是
**挡板贴到边上却到不了最边**，紧贴边界落下的星星接不到。

让 B 比 A 大一圈（`detector.roi_margin`，默认 60 像素），卡片在 A 边缘时仍
完整落在 B 内，中心就准；而映射时超出 A 的中心照旧被限幅到边缘，正是
"挡板贴边"想要的语义。

### 用鼠标框选（推荐）

```bash
python3 scripts/main.py --dry-run
```

窗口里：

1. 按 `r` → 在画面里点两下：先点**左上角**，再点**右下角**，
   框出卡片实际会移动到的极限范围。点下第二个角，A 立刻生效
2. 按 `0` → B 自动取"A 向外扩 60 像素"（想自己框就按 `t` 再点两下）
3. 按 `s` → 写回 `config.yaml`
4. 按 `q` → 退出

框选过程中整幅画面都归框选用，按钮不会抢你的点击；鼠标移动时会画
橡皮筋预览矩形并显示尺寸。按 `ESC` 可随时取消框选。

记不住按键没关系：**画面底部一直有这行提示**。真忘了可以把
`config.yaml` 里 `debug.show_guide` 改成 `true`，启动后画面中央会显示
一份图文步骤（默认关闭，免得挡住卡片）。

| 键盘 | 作用 |
|---|---|
| `r` / `a` | 框选 A（映射区） |
| `t` / `b` | 框选 B（检测区） |
| `0` | B 重置为"A 向外扩 60 像素" |
| `+` / `=` | B 每边各放大 10 像素（以中心为基准，不会越调越偏） |
| `-` | B 每边各缩小 10 像素 |
| `f` | B 切到整幅画面 / 切回 A+边距 |
| `s` | 保存 |
| `ESC` | 取消框选 |
| `q` | 退出 |

画面底部还有一排可点击的按钮（`框A` `框B` `B=A+60` …），它们画在
画面**内部**，所以窗口尺寸 = 摄像头画面尺寸，不会被屏幕裁掉。

界面截图：`images/ui_ok.png`（正常）与 `images/ui_warn.png`（B 太小报警）。

### 怎么知道 B 够不够大

**看 B 的颜色**：

| 颜色 | 含义 |
|---|---|
| 🟢 绿色虚线 | 正常 |
| 🔴 红色虚线 + 状态栏报警 | 检测框贴到了 B 的边界 → **色块很可能被裁过，中心会偏** |

看到红色就按 `+` 放大，直到把卡片移动到 A 的各个角落时都不再变红。

> 规则：`roi_margin` 必须 **大于红卡宽度的一半**。卡在 640×480 画面里约
> 90px 宽 → 至少 45；默认 60 留了余量。这条规则有测试守着
> （`tests/test_roi_editor.py::TestDefaultMargin`），改小了会被测出来。

### 框选要点

- **A 要框住色块实际会到达的极限位置**，不要凭感觉框大
- A 框太小 → 色块移出 A 后挡板贴边不动
- A 框太大 → 有效分辨率下降，挡板移动变"钝"
- B 太大 → 卡片在模型输入里占比变小，检出率可能下降；所以 B 够用就好
- 如果不确定，先 `B=A+60`，再跑 `--dry-run` 看实际效果

### 手动设置

也可以直接改 `config.yaml`：

```yaml
mapping:            # A：映射区域
  roi_x: 80
  roi_y: 60
  roi_w: 480
  roi_h: 360
detector:           # B：检测区域（roi_w/roi_h 为 0 表示自动取 A+边距）
  roi_x: 0
  roi_y: 0
  roi_w: 0
  roi_h: 0
  roi_margin: 60
```

## 第三步：方向与手感

### 方向对不对

跑空跑模式：

```bash
python3 scripts/main.py --dry-run --preview
```

**把色块从左往右移，看窗口上 `GAME` 的 X 是不是也在增大。**

| 现象 | 改法 |
|---|---|
| 色块右移，挡板左移 | `mapping.invert_x: true` |
| 色块下移，挡板反向 | `mapping.invert_y: true` |
| 色块左右移，挡板上下动 | `mapping.swap_xy: true`（摄像头转了 90°） |
| 挡板上下乱跑（只想要水平移动） | `mapping.fixed_y: 292` |

### 手感：平滑与死区

这两个参数直接决定挡板"跟手不跟手"：

```yaml
mapping:
  smoothing: 0.35    # EMA 系数
  deadband: 2.0      # 死区（游戏像素）
```

| 症状 | 调整 |
|---|---|
| 挡板一直在轻微哆嗦 | 减小 `smoothing`（如 0.2）；增大 `deadband`（如 4） |
| 挡板跟不上手，明显滞后 | 增大 `smoothing`（如 0.6）；减小 `deadband` |
| 挡板偶尔跳一大下 | 说明检测偶发跳到了别的物体，先解决误检（调大 `min_area`） |

**理解这两个参数**：

- `smoothing` 是**低通滤波**：输出 = α×新值 + (1-α)×旧值。α 越小越平滑。
  它会让挡板"柔和地"跟随，代价是响应变慢。
- `deadband` 是**死区**：变化小于阈值就完全不动。它能彻底消除静止时的
  抖动，而且不像 smoothing 那样引入滞后。

**调参顺序**：先调 `deadband`（解决静止抖动），再调 `smoothing`
（解决运动中的毛刺）。两个一起调会很难判断是哪个起了作用。

### 发送节奏

```yaml
loop:
  target_fps: 20.0        # 发送频率
  lost_frames: 5          # 连续几帧没检出算丢失
  reacquire_delay: 0.3    # 重新捕获后等多久再发
```

| 症状 | 调整 |
|---|---|
| 挡板偶尔莫名回退到按键控制 | 提高 `target_fps`；检查是不是丢帧 |
| 色块一晃过就"丢失" | 增大 `lost_frames` |
| 重新找到色块时挡板猛跳 | 增大 `reacquire_delay` |

## 常见标定误区

**误区 1：在一种灯光下标定，换环境就不管了**
色温变化会让 H 偏移。如果使用环境会变（白天/晚上），建议把
`custom_ranges` 的区间取得宽一些，或者接受需要重新标定。

**误区 2：用 min/max 而不是百分位**
个别高光像素的 H 可能完全跑偏。用 min/max 会得到一个巨大的区间，
把别的颜色也框进来。本项目用 5%~95% 百分位就是为了避免这个。

**误区 3：ROI 框得越小越"精确"**
ROI 越小，同样的像素误差映射到游戏坐标的偏移越大。ROI 应该刚好
覆盖活动范围，不要为了"提高灵敏度"而缩得过小。

**误区 4：一次性把所有参数都调了**
改一个参数，测一次效果，记下来。同时改多个会无法归因。
