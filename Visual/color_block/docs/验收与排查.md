# 第三部分：分层排查手册

## A. 摄像头问题

### A1. 完全没有 `/dev/video*`

```bash
python3 scripts/camera_check.py --probe-all
```

按输出提示排查：

| 检查 | 命令 |
|---|---|
| USB 总线上有没有设备 | `lsusb` |
| 内核有没有识别 | `dmesg \| tail -30` |
| 换个 USB 口 | 优先用板子上的 USB 3.0 蓝口 |

### A2. 有节点但抓不到帧

可能原因：

- **该节点不是采集口**。一个 UVC 摄像头常常暴露两个 `/dev/videoN`
  （一个采集、一个元数据）。用 `--probe-all` 逐个试。
- **被占用**。检查有没有别的程序开着：

  ```bash
  sudo fuser -v /dev/video0
  ```
  
  常见占用者：另一个 `preview.py` 窗口、`guvcview`、`motion`、浏览器。

### A3. 画面全黑

- 镜头盖没摘
- 自动曝光还没收敛（本项目的 `UsbCamera` 会预热丢 8 帧）
- 摄像头坏了（换电脑试）

### A4. 帧率远低于预期

USB 2.0 带宽限制。检查是不是协商成了 YUYV：

```bash
python3 scripts/camera_check.py --index 0
# 看输出的 FOURCC，应该是 MJPG
```

如果显示 YUYV 但配置写的是 MJPG，说明摄像头不支持 MJPG，或者
FOURCC 设置被忽略了。降到 640×480 或换 MJPG 摄像头。

## B. 检测问题

### B1. 完全检不到色块

按这个顺序查：

1. **确认色块在视野里** —— 用 `preview.py` 看，按 `d` 开掩膜显示。
   如果掩膜全黑，说明 HSV 区间不对。
2. **重新取色**：
   ```bash
   python3 scripts/color_pick.py --capture assets/captures/s2.jpg
   python3 scripts/color_pick.py --image assets/captures/s2.jpg --auto --write
   ```
3. **调小 `min_area`**。色块在画面里可能比你想的小：
   ```yaml
   detector:
     min_area: 100.0
   ```
4. **ROI 把色块排除在外了**。检查 `mapping.roi_*`。

### B2. 误检到别的物体

1. **调大 `min_area`** —— 最有效
2. **缩小 ROI** —— 把干扰物排除在检测区域外
3. **收紧 HSV 区间** —— 重新取色，或者手工把 S/V 下界调高
4. **用 `max_area`** —— 如果误检的是大面积同色背景：
   ```yaml
   detector:
     max_area: 5000.0
   ```

### B3. 检测位置有偏移

- 质心基于**轮廓面积**，如果色块有强反光导致一部分像素没被分割出来，
  质心会偏向另一侧。解决办法是放宽 V 的上界。
- 用圆形色块比方形更稳（质心不受旋转影响）。

### B4. 掩膜里色块有空洞

正常现象（反光点）。`morph_iterations` 的闭运算会填补，但迭代次数太多
会吃掉小色块。如果空洞很大，说明光照太强或有镜面反光，应该改物理条件
（换哑光材质的色块、调整灯光角度）。

## C. 串口问题

### C1. 找不到 `/dev/ttyS*`

**这是你这台板子的实际情况**：实测所有 10 个板载 UART 在设备树里
都是 `status = disabled`。

```bash
# 确认一下
for u in /proc/device-tree/serial@*; do
  echo "$(basename $u) = $(cat $u/status 2>/dev/null | tr -d '\0')"
done
```

**解决办法**（详见 `部署与接线.md`）：

- **推荐**：用 USB-TTL 转换器 → 直接得到 `/dev/ttyUSB0`，零配置
- 或者按文档启用 40pin UART 设备树插件

### C2. `Permission denied`

用户不在 `dialout` 组。

```bash
sudo usermod -aG dialout $USER
# 然后必须注销重新登录
```

### C3. 能打开但收不到 `OK`

这是**最常见也最需要系统排查**的问题。按顺序：

```bash
python3 scripts/serial_test.py --port /dev/ttyUSB0
```

如果一直超时，依次检查：

| # | 检查项 | 怎么查 |
|---|---|---|
| 1 | STM32 在运行吗 | 屏幕有显示吗？换成按键控制能用吗？ |
| 2 | 固件调了接收初始化吗 | 代码里有没有 `BSP_GameSerial_Start()` |
| 3 | **TX/RX 交叉了吗** | 交换两根线再试 |
| 4 | **共地了吗** | 万用表量两边 GND 是否导通 |
| 5 | 波特率一致吗 | 两边都是 115200？ |
| 6 | 选对串口了吗 | 用 `--probe` 自动找 |

**回环测试**可以帮你定位是本地问题还是对端问题：

```bash
# 把 USB-TTL 的 TX 和 RX 用杜邦线短接
python3 scripts/serial_test.py --port /dev/ttyUSB0 --loopback
```

- 回环成功 → 本地串口正常，问题在对端或接线
- 回环失败 → 本地串口本身有问题

### C4. 收到 `ERROR` 而不是 `OK`

说明能通信，但帧被判为无效。原因大概率是：

- **波特率不一致** → 收到的是乱码，CRC 必然失败
- **字节序写反** → 不太可能，本项目有测试覆盖
- **固件版本不是本仓库的** → 检查 `bsp_board.c` 里的 CRC 实现是否一致

用已知正确的帧验证：

```bash
python3 scripts/serial_test.py --raw "AA 55 06 01 D4 00 42 02 00 7D"
```

这帧的 CRC 是由固件原版 C 函数算出来的。如果它也回 `ERROR`，
那问题一定在波特率或接线，而不是你的坐标数据。

反过来，验证 STM32 的校验逻辑是否正常工作：

```bash
python3 scripts/serial_test.py --bad-crc
```

预期 STM32 回 `ERROR`。如果它回了 `OK`，说明固件的校验逻辑有问题。

## D. 追踪行为问题

### D1. 挡板不动

1. `main.py` 的收尾统计里 `发送数据帧` 是 0 吗？
   - 是 → 一直没检出色块，走 B1
2. `单片机回 OK` 是 0 吗？
   - 是 → 串口问题，走 C3
3. 屏幕上的挡板是不是被按键控制接管了？
   - 检查 `control_type` 是不是 1

### D2. 挡板方向相反

```yaml
mapping:
  invert_x: true      # 左右反
  invert_y: true      # 上下反
  swap_xy: true       # 摄像头转了 90°
```

### D3. 挡板抖动

按这个顺序调，一次只改一个：

1. 增大 `mapping.deadband`（如 2.0 → 5.0）—— 先解决静止抖动
2. 减小 `mapping.smoothing`（如 0.35 → 0.2）—— 再解决运动毛刺
3. 若还抖，说明检测本身在跳（误检），走 B2

### D4. 挡板反应迟钝

和 D3 相反：增大 `smoothing`、减小 `deadband`。

### D5. 挡板偶尔回退到按键控制

`loop.target_fps` 太低，或者检测中断太久触发了丢失判定。

```yaml
loop:
  target_fps: 25.0
  lost_frames: 8
```

### D6. 挡板贴边不动

色块移出了 **A（映射区域）** 范围。跑 `python3 scripts/main.py --dry-run`，
按 `r` 在画面里点两下重新框一个更大的范围，再按 `s` 保存。

### D7. 挡板能贴边，但**到不了最边上**（边缘的星星接不到）★

这是本项目最花心思修的一个问题，特征很典型：

- 挡板能跟着卡片走，方向也对
- 但把卡片移到画面左右最边上时，挡板总差那么一点点贴不到墙
- 紧贴边界落下的星星接不到

**原因**：卡片中心移到 **A 的边界**时，卡片有一半落在 A 之外。如果检测区域
和 A 是同一个框，模型只能看到剩下的那一半，算出来的中心是**可见部分的
中心**而不是真实中心 —— 于是挡板永远差半个卡片宽度。

**判断方法**：看画面里 **B（检测区域，绿色虚线）** 的颜色。

| B 的颜色 | 含义 | 处理 |
|---|---|---|
| 🟢 绿色虚线 | 正常 | —— |
| 🔴 红色虚线 + 状态栏报警 | 检测框贴到了 B 的边界，卡片被裁过 | 按 `+` 放大 B |

**先量化一下问题**（无需硬件，直接看数字）：

```bash
python3 scripts/demo_edge_center.py
```

会打印出"卡片中心顶到 A 边界时，两种配置各自偏多少像素"，
并把偏差换算成游戏像素 —— 例如 B=A 时"挡板离墙还差约 37 游戏像素"，
B=A+60 时只剩 4 像素。**这个 37 就是你接不到边缘星星的原因。**

**修复**：让 B 比 A 大一圈，且 **`roi_margin` 必须大于卡片宽度的一半**。

```yaml
detector:
  roi_margin: 60     # 卡片在画面里约 90px 宽 → 至少 45，默认 60 留余量
```

按 `0` 一键把 B 重置成"A 向外扩 60 像素"，再按 `s` 保存。

**验证**：把卡片沿 A 的**四条边**和**四个角**走一圈，B 全程保持绿色、
状态栏不报警，就说明 B 够大了。然后跑闭环看挡板能不能贴到最边上。

> 截图对照：`images/ui_warn.png`（红色报警）vs `images/ui_ok.png`（正常）。

### D8. 窗口弹出来了，但画面上没有任何界面（没有两个大框 / 按钮 / 指引）

用户实际报过一次：窗口正常、检测也正常、坐标在跳，但**看不到你说的那个
控制面板**。特征很好认：

- 画面上只有视频 + 左上角那几行 `cam=/GAME=/TX:` 文字
- 没有黄色 A 框、没有绿色虚线 B 框
- 底部没有按钮条，也没有 A/B 的数值

**原因**：ROI 控制面板是在 `ColorTrackingPipeline.open()` 里创建的，而
`scripts/main.py` 以前是"自己开摄像头、直接调 `run()`"，**从没调用过
`pipeline.open()`** —— 于是编辑器压根没建，`roi_editor is None`，
所有叠加都被跳过。

**现在已经从两头堵住**：

1. `main.py` 老老实实调用 `pipeline.open()`
2. `run()` 里也调一次幂等的 `_ensure_preview_controls()` ——
   不管调用方走不走 `open()`，只要进主循环，面板就一定在

**自查命令**：

```bash
# 应该看到 A 映射区 / B 检测区 的数值和按钮条
python3 scripts/main.py --dry-run
```

对应回归测试：`tests/test_robustness.py::TestControlsExistWithoutCallingOpen`
（完全模仿 main.py 的用法：只开摄像头、不调 open()，断言面板必须被创建并画到画面上）。

### D9. 画面里没有文字 / 文字变成空白

`cv2.putText` 画不了中文（也不报错，字就是不见了），所以界面文字走
Pillow 渲染。板子上应该有 Noto Sans CJK 或文泉驿字体；万一没有，
程序会**自动丢掉画不出来的字**而不是画乱码。

查一下：

```bash
python3 -c "from src.text_cjk import describe; print(describe())"
# 正常：中文字体：/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc
# 异常：未找到中文字体，界面上的中文会被省略（数字与英文不受影响）
```

装字体（需要联网）：

```bash
sudo apt install fonts-noto-cjk
```

## E. 系统层面问题

### E1. 中文输入法突然失效

与本项目无关，是鲁班猫上 GNOME + ibus 的已知小毛病。

**最快恢复**：打开终端随便敲一个字（会触发 ibus 引擎按需启动）。
或者：

```bash
ibus restart
```

### E2. 内存/CPU 占用高

本项目正常占用：

- CPU：单核 10~25%（20fps，640×480）
- 内存：约 200~300 MB（主要是 OpenCV 的加载）

如果明显超出，检查是不是开了 `debug.save_frames` 在往磁盘写图。

### E3. 磁盘被写满

```bash
# 清理标定残留
rm -f assets/captures/*.jpg assets/output/*.jpg
```

长期运行时关闭 `debug.save_frames`。
